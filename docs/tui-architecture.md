# TUI architecture and feature parity

**Status (2026-11-09):** S16.1–S16.6, S16.9 and S16.10 are merged. The standalone TUI covers the current library, lifecycle, guest serial, state/trust and signing/package workflows. The public `libghostty-vt` PTY smoke passes on Linux x86_64, macOS arm64 and Windows x86_64. The custom GPUI terminal view passes Linux Xvfb host interaction checks for keyboard input, ANSI output, selection, copy/paste, resize, quit and PTY cleanup. The view is behind the optional `embedded-terminal` feature; release package workflows do not enable or bundle that feature. Its Xvfb smoke does not boot a guest through the embedded session. Native macOS/Windows GPUI hosts and the embedded guest workflow remain open for S16.8 acceptance. Native UX review is deferred to later Figma-led work.

## Product contract

Rootglass provides a standalone Ratatui frontend through `rootglass tui`. It covers the existing Rootglass command and app workflows, including bundle verification/import, the installed library, trust/preflight reporting, run lifecycle, persistent state, the guest serial console, and developer signing/packaging. A supplied bundle path is accepted by the TUI entry point so a platform file association can pass a `.glass` path through the existing package workflow.

The TUI must be testable without a display server or a real terminal. Keep its controller and renderer independent of GPUI, and exercise rendering with Ratatui's `TestBackend` and a deterministic fake service. Keep filesystem, signature, import, and process work off the input/render loop.

The GPUI application will host the TUI through an embedded terminal surface backed by libghostty. The terminal host handles terminal input, output, resize, clipboard, and lifecycle; the TUI session owns Rootglass interaction and calls shared Rust APIs. The session adapter must not expose an arbitrary shell. The terminal host is the *outer* terminal that displays the Ratatui app; the TUI's guest-console pane separately reads and writes the guest's serial stream through `rootglass-app`.

The TUI and GPUI host must not reimplement signature/trust policy, registry transactions, state locking, launch checks, or lifecycle rules. The TUI session calls `rootglass-app` APIs; signing/package flows call `rootglass-signature` APIs. Do not shell out to the CLI to perform an individual Rootglass operation. The current desktop integration starts its own executable in a private PTY process with an internal TUI-session argument. It runs the shared TUI library and exposes no shell command surface.

The current `rootglass validate` command only validates the manifest; it does not verify the DSSE signature or publisher trust. The TUI's inspect/verify flow must call `AppService::inspect` and make the stronger result explicit. The current service exposes installed-library list/remove and state selection at run time, but not state CRUD through `AppService`; S12.2 must establish that contract before TUI state controls ship. The current desktop controller composes restart as stop/start; there is no separate public restart method.

Production TUI startup must follow the desktop's trust configuration behavior: load the local publisher trust config and fall back to `AppService::deny_all()` with a visible blocked state if the config is missing or invalid. Do not use `AppService::new()` in production mode because its default trust store contains the example fixture key. The proposed offline policy is in [ADR-0001](adr/0001-offline-publisher-trust.md); the desktop's config-path resolver is currently private to its UI model, so S16.3 should share or safely reuse that resolution rule instead of introducing a second platform-specific path.

The TUI must preserve signed release immutability and the existing development-only `.img` exception boundary. In particular, production signing/package operations cover generated `.img` assets as signed subjects, and the current signing API reads keys from an external secret file. The standalone TUI has no native secret-file picker on any platform, so users enter the path to an external key file; the existing CLI `sign` and `package` commands remain supported. Never paste, store in TUI state, or render private key bytes. Agent-backed signing requires an explicit library API before it is offered.

## Standalone terminal session

`rootglass tui [bundle-path]` runs the Ratatui session directly, with no GPUI window or installed Ghostty application. It requires interactive stdin and stdout, and also runs over a full-duplex PTY for a future embedded-terminal host. The terminal adapter owns Crossterm raw mode, the alternate screen, input events, resize redraws, and mode restoration. It restores the terminal on normal quit, Ctrl-C, returned errors, and Rust unwinding; an active guest is stopped before the process exits.

The current keys are `o` to enter a bundle path, Up/Down to select an installed bundle, `b` to boot, `s` to stop, `r` to restart, `f` to refresh the library, Enter to type a guest serial line, and `q` or Ctrl-C to exit. Esc cancels a path or serial prompt and exits from the main view. The controller and Ratatui `TestBackend` remain usable without the terminal adapter.

## GPUI and libghostty contract

Keep GPUI Kit `=0.9.0` as the application-window framework. Ratatui is the TUI renderer/controller; libghostty is only the embedded terminal host. The TUI and host communicate over a full-duplex terminal session, including key input, terminal output, resize and clipboard operations. The adapter owns the terminal-session/PTY lifecycle and shuts it down with the GPUI window.

The maintainer approved using public [`libghostty-vt`](https://github.com/ghostty-org/ghostty/tree/main/include/ghostty/vt) with a custom GPUI renderer and PTY/session adapter. Upstream [`include/ghostty.h`](https://github.com/ghostty-org/ghostty/blob/main/include/ghostty.h) labels the full embedding C API internal and says the macOS app is its only consumer. Ghostty's [README](https://github.com/ghostty-org/ghostty/blob/vt-1.0.0/README.md) describes its macOS GUI as SwiftUI and Linux GUI as GTK; neither uses GPUI Kit. The official minimal embedder, [Ghostling](https://github.com/ghostty-org/ghostling), uses Raylib, also not GPUI Kit. `libghostty-vt` provides terminal state and render data but leaves the PTY and drawing to its embedder. The spike README records upstream v1.0.0 target and dependency-license information; release packaging still needs to preserve those notices and qualify each Rootglass host.

The [cmux project](https://github.com/manaflow-ai/cmux) is a useful architectural reference, not a reusable GPUI view. Its macOS desktop app uses a native Swift/AppKit Ghostty surface; its separate [`cmux-tui`](https://github.com/manaflow-ai/cmux/tree/main/cmux-tui) is a Rust/Ratatui application backed by a Rust wrapper around `libghostty-vt`. Its [TerminalBytesDemo](https://github.com/manaflow-ai/cmux/tree/main/cmux-tui/apps/macos/TerminalBytesDemo) shows a clean terminal-byte boundary: Rust owns the PTY session and VT parser while the native view handles input/IME, selection, paste, and resize. These examples support Rootglass's separate TUI/session and host-surface responsibilities, but neither provides a GPUI Kit component. The cmux desktop source is GPL-3.0-or-later, so Rootglass uses it as a design reference only.

The headless S16.6 spike in [`prototypes/libghostty-vt-ratatui`](../prototypes/libghostty-vt-ratatui/README.md) pins `libghostty-vt` 1.0.0 and exercises PTY output, public write-to-PTY replies, render-state access, key and paste encoding, resize, selected-text extraction, and cleanup on Linux x86_64. Its focused CI workflow verifies upstream signatures and checksums, builds the pinned library and runs that PTY smoke. It confirms that `libghostty-vt` leaves PTY and drawing to the embedder; the spike does not qualify the GPUI surface, native clipboard, accessibility, or any desktop platform.

The maintainer approved Linux x86_64, macOS arm64, and Windows x86_64 as the S16.6/S16.7 qualification targets. Ghostty's v1.0.0 packaging guide lists those operating systems among Tier 1 `libghostty-vt` targets; Windows uses the GNU ABI library, whose import library can be linked by MSVC applications. These are approved targets, not a claim that Rootglass builds or the GPUI view is qualified on them. The native PTY matrix does not replace an interactive GPUI host check. Do not claim platform support before native host checks pass. Do not depend on the internal API or replace libghostty with the standalone Ghostty app or another emulator.

## Headless and host validation

Headless checks cover the same TUI controller and rendering code used by the standalone frontend: Ratatui `TestBackend`, deterministic service fakes, temporary library/state/trust directories, stale-operation and `RunId` handling, serial input/output, and fake-child cleanup. These checks do not need X11, a native window, or QEMU.

The Linux Xvfb host smoke covers keyboard focus/input, resize, keyboard selection, clipboard copy/paste, ANSI rendering and cleanup when the GPUI window closes. It does not prove native macOS/Windows GPUI behavior, screen-reader accessibility, or a real guest serial login/input/output journey; retain those as host acceptance work. A missing desktop host is a blocked acceptance result, never a headless pass. Reuse existing A-02/A-05/A-07 evidence only when its revision and scenario still apply. Keep the R3 deferred features outside this workstream.
